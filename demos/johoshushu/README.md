# 定期的な情報収集の自動化（デモ）

競合の価格や補助金の公募情報を定期的に取りに行き、**前回との差分だけ**をレポートにする仕組みのデモです。
`index.html` をブラウザで開くだけで動きます（インストール不要）。

> **掲載しているデータはすべてデモ用の架空のものです。**
> サイト名・商品名・価格・在庫状況・制度名・補助上限額・締切のいずれも、このデモのために作ったものです。
> **実在するサイトへのアクセスは一切行っていません。** 「前回取得分」と「今回取得分」の2世代のデータを
> ファイル内にあらかじめ持たせ、実行ボタンで両者を突き合わせているだけです。通信は発生しません。

---

## 解消したい状態

- 競合の価格を毎朝チェックしている
- 補助金・公募情報を定期的に見に行っている
- 更新があったかどうかを目視で確認している

いずれも、**情報収集が人の習慣に依存していて、抜けても誰も気づかない**という状態です。
このデモは、その状態を「決まった時刻に機械が取りに行き、変わったところだけが届く」形に置き換えたときに
何がどう見えるのかを、画面で確認していただくためのものです。

---

## 画面の構成（7つの節）

| 節 | 内容 |
|---|---|
| 一　収集設定 | 対象サイト・取得項目・実行頻度を選ぶ。ここを変えると下の内容がその場で変わる |
| 二　収集結果 | 取得したデータの一覧。今回と前回を横に並べて表示 |
| 三　差分レポート | **中心の画面。** 変わった行だけを抜き出し、区分ごとに分けて表示 |
| 四　通知ルール | 「価格が5％以上下がったら」などの条件。該当行が差分レポートで強調される |
| 五　実行履歴 | いつ実行され、何件取得し、何件変わったかの記録。失敗した回も残る |
| 六　手作業との比較 | 対象件数と目視秒数を入れると削減時間が出る |
| 七　実装と運用について | 実際の納品物の形、収集先サイトの取り扱い、注記 |

上部の「用途を選ぶ」で、**競合の価格・在庫**と**補助金・公募情報**の2つを切り替えられます。
同じ画面のコードのまま、対象・項目・通知条件・データだけが入れ替わります。

## 差分レポートの区分

前回取得分と今回取得分を、**選択中の項目だけ**で突き合わせて分類します。

| 区分 | 判定 |
|---|---|
| 値上がり（増額） | 中心の数値項目が増えた |
| 値下がり（減額） | 中心の数値項目が減った |
| 新規 | 今回だけに存在する |
| 消えた | 前回だけに存在する |
| 項目の変更 | 中心の数値以外（在庫状況・締切・受付状況など）が変わった |
| 変化なし | 選択中の項目がすべて前回と同じ |

**変化なしの行は、確認しなくてよい行です。** 全件を見比べる代わりに、差分レポートの行だけを見ます。

デモデータは、競合の価格が延べ30件、補助金が延べ24件です。いずれも上の6区分をすべて含みます。

### 設定を変えると結果が変わることの確認

- **取得項目から「在庫状況」を外す** → 在庫だけが変わっていた行が「変化なし」に移り、確認対象が減ります
- **取得項目から「販売価格」を外す** → 値上がり・値下がりの区分が消え、価格に関する通知ルールが自動的に無効になります
- **収集対象を1サイトに絞る** → そのサイトの行だけが残ります
- **通知ルールのしきい値を5％→2％に下げる** → 該当件数が増えます

## 色の使い分け

臙脂（赤茶）は **「要注意」の用途にだけ**使っています。値の向きと注意の向きは用途によって逆になるため、
色は用途ごとに定義しています。

| 用途 | 臙脂＝要注意 | 紺 |
|---|---|---|
| 競合の価格 | 値上がり（追随の判断が要る） | 値下がり（こちらの好機） |
| 補助金 | 減額（計画の見直しが要る） | 増額（好材料） |

そのほか、想定値による試算（削減時間・人件費換算）と、取得に失敗した実行記録にも臙脂を使っています。

## 手作業との比較の計算式

```
手作業（月あたり）　＝ 対象件数 × 1件あたりの目視秒数 × 月あたりの実行回数
自動化した後（月あたり）＝ 変化した件数 × 1件あたりの目視秒数 × 月あたりの実行回数
削減できる時間　　　＝ 手作業 − 自動化した後
```

自動化しても確認がゼロになるわけではありません。**「変わった行だけを見る時間」は残ります。**
その分を差し引いた数字を出しています。時給は入力された想定値であり、実績値ではありません。

月あたりの実行回数は、一の「実行の頻度」の設定に連動します。
頻度を「1時間ごと」にすると手作業の数字が現実離れした値になりますが、それは計算の誤りではなく、
**その頻度は人手では回せない**という意味です。

## 他の用途への転用

ファイル冒頭の `CONFIG` と `PRESETS` を差し替えるだけで、別の情報収集のデモになります。
画面側のコードは、収集対象の中身も項目の意味も知りません。

```js
{
  key: "kakaku",
  label: "競合の価格・在庫を見張る",
  targets: [ /* 収集先サイト。label（正式名）と short（表用の略称） */ ],
  idField: { key: "name", label: "商品名" },   // 行を見分ける鍵
  subField: { key: "model", label: "型番" },   // 補助的な表示項目
  fields: [
    // primary: true が「値の上下」を見る中心の項目
    { key: "price", label: "販売価格", unit: "円", type: "money", primary: true, defaultOn: true },
    { key: "stock", label: "在庫状況", type: "status", defaultOn: true },
  ],
  kindLabels: { up: "値上がり", down: "値下がり" },
  kindTone:   { up: "caution",  down: "accent" },   // 臙脂をどちらに割り当てるか
  rules: [ /* 通知条件のひな形 */ ],
  rows:  [ /* prev（前回取得分）と curr（今回取得分）の2世代データ */ ],
}
```

`fields` の `type` は `money` / `num` / `status` / `date` の4種類です。
`money` と `num` は変化率（％）を計算し、`status` と `date` は前後の値をそのまま並べます。

通知ルールの `kind` は次の6種類です。参照している項目が取得対象から外された場合、
そのルールは自動的に無効になり、画面上でもその旨が表示されます。

| kind | 判定 |
|---|---|
| `pct-up` / `pct-down` | 指定項目が、しきい値（％）以上に増えた／減った |
| `status-to` | 指定項目が、特定の値に変わった |
| `field-changed` | 指定項目が、何であれ変わった |
| `added` / `removed` | 今回から現れた／今回は取得できなかった |

## 技術構成

- React 18 + Tailwind CSS（いずれもCDN）、Babel standalone による**1ファイル完結**
- Babel は `registerPreset` で classic runtime を指定
- **`localStorage` は不使用。** Cookie・外部送信も行っていないため、リロードで初期状態に戻ります
- 配色・字送りは、リポジトリ直下の `index.html`（業務の悩み 索引）と同一の `:root` 変数を使用。
  新しいトークンは定義していません
- 影・角丸・グラデーション・ダーク背景・装飾アイコン・絵文字・英語見出しは不使用。区切りは罫線のみ
- 見出しは明朝、本文はゴシック。Webフォントは読み込みません
- スマートフォン幅（375px）まで対応。表は各表の内側で横スクロールします

## 実際の納品物

このデモはブラウザ上の見本です。実際にお渡しするものは次の形になります。

1. **納品物は Python のスクリプトです。** ブラウザで開く画面ではありません。
   収集対象・取得項目・通知条件は設定ファイルに切り出し、対象が増えたときは1行足すだけで済む形にします
2. **サーバー上で定期実行し、差分レポートをメールで送ります。**
   受け取る側は、届いたメールを見るだけです
3. **取得した値は世代ごとに保存します。** 前回と今回の2世代だけでなく過去の推移を残し、
   値上がりが続いているのか一時的なものかを判断できるようにします
4. **取得に失敗したときは、失敗したこと自体を知らせます。**
   何も届かない状態を「変化がなかった」と取り違えないためです

### 収集先サイトの取り扱い

実施前に、**収集先サイトの利用規約と robots.txt を確認し、許容される範囲でのみ実施します。**
自動取得を禁じているサイトは対象から外します。取得の間隔は相手のサーバーに負荷をかけない範囲に抑え、
公式に API や配信データが提供されている場合は、そちらを優先して使います。
この確認は着手前の作業に含みます。確認の結果、対象にできないサイトがあった場合は、その旨をお伝えします。
