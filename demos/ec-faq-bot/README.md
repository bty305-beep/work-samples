# ECカスタマーサポート自動化 デモ

`index.html` をブラウザで開くだけで動きます。インストール・ビルド不要、1ファイル完結です。

お客様の問い合わせが

**選択式FAQ BOT → AI BOT → LINE / Gmail / 問い合わせフォーム → 一元管理 → AI返信・AI下書き → 必要な案件のみ有人対応**

と流れていく過程を、実際に操作しながら確認できます。

---

## この案件の核心：どの段階で何件減るか

「有人問い合わせを50〜70%削減」という数値目標を、画面上で追える形にしています。

| 段階 | 件数 | 割合 |
|---|---|---|
| 総問い合わせ数 | 1,000件 | — |
| 選択式FAQ BOTで解決 | 430件 | 43% |
| AI BOTで解決 | 190件 | 19% |
| **有人対応に残る** | **380件** | **38%** |

**削減率 62.0%** — 目標帯 50〜70% の中央です。

運営側の画面上部に、この内訳を積み上げバーと「1,000件 → FAQで−430 → 570件 → AIで−190 → 380件」という流れで表示しています。
削減の効果がどの段階から来ているかが、数字を追わなくても見て分かります。

有人対応380件のうち250件には**AIの返信下書きが付いています**。ただし人が確認して送信するため、これは削減率には含めていません。削減率は「人の手を一切介さずに完結した件数」だけで計算しています。

## 【1】お客様側のチャット画面

1. **選択式FAQ** — ECでよくある6分類（配送状況／返品交換／サイズ・素材／支払い／キャンセル・変更／在庫）からボタンを辿ると回答に到達します。階層は何段でも設定できます（返品交換は3階層）
2. **AI BOT** — 「解決しなかった」を押すと自由入力に切り替わります。言い回しが違っても意図を判定して回答します
3. **有人対応** — AI BOTでも解決しない場合、エスカレーションフォームが出ます。連絡方法（LINE / メール / フォーム）を選んで送信できます

画面の右端に、**その段階までで何割が解決するか**の想定値を常時表示しています。今どこにいて、あと何割がこの先に流れるのかが分かります。

送信したエスカレーションは、**運営側の一元管理画面にそのまま「人間対応必要」として追加されます。** 上部のタブで切り替えて確認できます。

---

## 【2】運営側の一元管理画面

- LINE / Gmail / 問い合わせフォームからの問い合わせを、**1つの受信トレイ**に集約
- 流入元は色とバッジで区別（LINE=緑 / Gmail=赤 / フォーム=藍）
- ステータスは4種類 — AI解決済み / AI下書きあり・要確認 / 人間対応必要 / 対応済み
- **「AI下書きあり」の行を開くと返信文が表示され、そのまま送信するか、編集してから送信できます**
- 「人間対応必要」の行には**自動返信を止めている理由**を明記。ボタン1つでAI下書きを作らせることもできます（判断は人、文面作成はAI）

## 設定の差し替え

ファイル冒頭の設定オブジェクトを書き換えるだけで、別ブランドの仕様になります。コード本体は触りません。

| 設定 | 内容 |
|---|---|
| `BRAND` | ブランド名・挨拶文・受付時間 |
| `BASELINE` | 実績のベースライン。削減率はここから算出されます |
| `TARGET` | 目標帯（初期値 50〜70%） |
| `FAQ_TREE` | 選択式FAQの選択肢ツリー。`children` で入れ子、`answer` で回答 |
| `AI_RESPONSES` | AI BOTの応答。キーワードと返答文の組 |
| `ESCALATION_FORM` | 有人対応フォームの入力項目 |
| `SOURCES` | 流入元の定義（ラベル・色） |
| `STATUSES` | ステータス定義。`counts` で削減率の集計区分を指定 |
| `INBOX_SEED` | 受信トレイの初期データ |

## 実装時の構成

本デモは画面確認用のため、AI BOTの応答はあらかじめ用意した内容を返しています（APIは呼びません）。

実装時は次の処理を**すべてサーバー側**で行います。

- **AIによる回答生成・返信下書きの作成** — 社内のFAQ・過去の対応履歴を参照して生成。APIキーはブラウザに出しません
- **LINE（Messaging API）／Gmail（Gmail API）／フォームPOSTの受信** — 各チャネルのWebhookを受け取り、共通のスキーマに正規化して1つのテーブルに保存します。一元管理画面が成り立つのはこの正規化があるためです
- **返信の送信** — 受信と同じ経路を逆にたどるため、担当者はチャネルを意識せずに返信できます
