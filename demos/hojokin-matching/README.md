# 補助金・助成金マッチング PoC（試作版）

事業者の情報から、利用できる可能性のある補助金・助成金を提案する仕組みの試作です。
`index.html` をブラウザで開くだけで動きます（インストール不要）。

> **掲載している制度はすべて架空です。**
> 制度名・要件・上限額・補助率・公募時期は、このデモのために作ったものです。
> 実在する制度の内容を示すものではありません。本番では、公募中の制度データを
> 出典URL・取得日時つきで取り込みます。

---

## このPoCで検証したいこと

発注内容にある「マッチング精度」と「技術的な実現可能性」の2点に絞っています。
そのため、見た目の作り込みよりも **なぜその制度が該当したのかを画面から追えること** を優先しました。

具体的には、1件ごとに次を必ず表示します。

- **適合度（％）とその内訳** — どの要件に何点入ったかを表で確認できます
- **該当理由** — 「従業員数 20名 は、要件『従業員数 20名以下（小規模事業者）』に該当します」のように、入力値と要件を突き合わせた文で出します
- **満たしていない条件・要確認事項** — 入力情報だけでは判定できない要件（書類要件など）を隠さずに出します
- 補助上限額 / 補助率 / 公募時期の目安

必須要件（法人限定、対象地域限定など）を満たさない制度も、画面から消さずに
**対象外の理由をつけて別枠に表示** します。候補に出てこない理由が分からない状態を作らないためです。

## 画面の構成

| タブ | 内容 |
|---|---|
| ① 事業者情報とマッチング | 入力フォームと結果。入力を変えると結果がその場で変わります |
| ② 適合度の計算ロジック | 配点表、判定の3値、必須要件の扱い、いまの入力での全10件の計算結果マトリクス |
| ③ 本番実装に向けて | 情報収集の方法、精度を上げる方法、このPoCで割り切っている点 |

入力項目は、事業形態（法人／個人事業主）・業種・従業員数・所在地（都道府県）・設立年・直近売上規模・
検討している取り組み（設備投資／IT導入／人材採用／販路開拓／事業承継／省エネ、複数選択）です。

左上の「入力例で試す」から4パターンを切り替えられます。同じ10件のデータでも、
条件によって候補と順位が入れ替わることを確認できます。

---

## 適合度の考え方（加点式）

要件を1件ずつ判定して配点を足し上げ、その制度の満点で割って百分率にしています。
類似度スコアのような「理由を後から説明できない数値」は使っていません。

```
適合度(%) = 獲得点の合計 ÷ その制度の満点 × 100
```

| 要件区分 | 配点 |
|---|---:|
| 取り組み（何をしたいか） | 35 |
| 業種 | 15 |
| 規模（従業員数） | 15 |
| 事業形態 | 10 |
| 地域 | 10 |
| 事業年数 | 10 |
| 売上規模 | 5 |
| 要確認（1件あたり） | 5 |

判定は **合致 / 不一致 / 要確認** の3値です。
判定できないものを不一致に丸めると本来使える制度を落とし、合致とみなすと使えない制度を勧めてしまうため、
**0点のまま「要確認」として画面に出す** 方針にしています。
そのため各カードには「現在の適合度」と「要確認がすべて満たされた場合の最大値」の両方を表示します。

要件は3層に分けています。

1. **必須要件（ゲート）** — 外れたら対象外に振り分ける
2. **加点要件** — 順位付けに使う
3. **要確認要件** — 判定できないので0点のまま提示する

## 技術構成

- React 18 + Tailwind CSS（いずれもCDN）、Babel standalone による1ファイル完結
- 保存機能なし（localStorage不使用のため、リロードで初期状態に戻ります）
- 制度データは同ファイル内の `PROGRAMS` 配列（架空10件）

本番では、この配列を「収集 → 構造化 → 人によるレビュー」を経た制度DBに置き換える想定です。
マッチングの判定はルールエンジンで行い、LLMは公募要領からの要件抽出に限定します
（判定にLLMを使うと、同じ入力で結果が揺れ、根拠を再現できなくなるため）。

詳しくは画面の「③ 本番実装に向けて」タブに記載しています。
