# LINE公式アカウント 運用設計 デモ

`index.html` をブラウザで開くだけで動きます。インストール・ビルド不要、1ファイル完結です。意匠は索引ページ（リポジトリ直下の `index.html`）と共通で、冒頭から索引ページに戻れます。

届いたメッセージが

**受信 → 振り分け（自動応答／受付だけ自動返信／人が対応） → 未返信の検知 → 担当者へ再通知 → 店長へ引き上げ**

と流れていく過程を、実際に操作しながら確認できます。

---

## この画面が言いたいこと：放置は、性格ではなく設計の問題です

索引ページの悩み「LINE公式を作ったが、放置されている」からの行き先です。

実際のクチコミに、こういう声がありました。**「LINEで連絡と言われたが、都合の悪い件は何日経っても返信が来ない」**。

返ってこないのは、答えにくい件です。予約が取れない、値引きを求められた、苦情が来た。人は答えにくい件を後回しにします。**放置は担当者の性格の問題ではなく、後回しにしたことを誰も検知していないという設計の問題です。**

**このデモの中心は自動応答ではなく、未返信の検知のほうです。** 自動応答で片づくのは答えが一つに決まる質問だけで、苦情・予約の変更・例外の相談は必ず人に残ります。残った分を放置しない仕組みがないまま自動応答だけを入れると、返信が早い件といつまでも返らない件の差が広がります。

初期状態（デモの現在時刻 2026年8月17日(月) 11:30）の内訳です。

| 分類 | 件数 | 内容 |
|---|---|---|
| 自動応答済 | 12件（40%） | 営業時間・駐車場・料金。人の手は動いていません |
| 未対応 | 5件 | 人が返信する必要があり、まだ目標時間内 |
| **要対応** | **11件** | **初回返信の目標1時間を超過。再通知が発生しています** |
| 対応済み | 2件 | 人が返信して閉じたもの |

最も長い未返信は **10.8営業時間**（金曜夕方に届いた予約変更）。この件には5回の通知が発生し、店長へ引き上げ済みになっています。

---

## 【一】受信トレイ

届いたメッセージを **未対応・自動応答済・要対応** の3分類で表示します。分類は人が付けているのではなく、振り分けルールと初回返信の目標時間から自動で決まります。

- 並び順は要対応 → 未対応 → 自動応答済 → 対応済み。同じ分類の中では古いものが上に来るため、**放置されているものほど上に出ます**
- 行を開くと、届いた本文・当たったルール・**一致した語**・送られた自動返信の文面・未返信の経過時間（営業時間と実時間の両方）が読めます
- 苦情の行には「自動応答に回していない理由」を表示します。なぜ人に回ってきたのか説明できない状態を作らないためです
- 「返信して対応済みにする」を押すと、その件の再通知が止まります

---

## 【二】振り分けルール

どんな内容を自動応答に回し、どんな内容を人に残すかを画面上で設定します。**扱いを切り替えると、上の要約と受信トレイの分類がその場で変わります。**

扱いは3つです。「自動応答で完結」と「人が対応」の2択にしていないのは、**受付の自動返信を送っても人の対応は残る**ことを見せるためです。

| 扱い | 顧客に返るもの | 分類 | 未返信の検知 |
|---|---|---|---|
| 自動応答で完結 | 回答そのもの | 自動応答済 | 対象外 |
| 受付だけ自動返信 | 受け付けた旨と、いつ返信するか | 未対応（超過すると要対応） | **対象** |
| 人が対応 | なし | 未対応（超過すると要対応） | **対象** |

ルールは上から順に判定し、最初に当たったものを使います。順番が意味を持つのは、「予約の変更をお願いしたのに返信が来ない」のように複数のルールに当てはまる文があるためです。

| 順 | ルール | 初期の扱い | 該当 |
|---|---|---|---|
| 1 | 苦情・不満の申し出 | 人が対応（**固定**） | 4件 |
| 2 | 予約の変更・キャンセル | 受付だけ自動返信 | 5件 |
| 3 | 予約の依頼 | 受付だけ自動返信 | 5件 |
| 4 | 営業時間・定休日の質問 | 自動応答で完結 | 4件 |
| 5 | 駐車場・行き方の質問 | 自動応答で完結 | 4件 |
| 6 | 料金・メニューの質問 | 自動応答で完結 | 4件 |
| 7 | 上のどれにも当てはまらないもの | 受付だけ自動返信 | 4件 |

- **苦情は自動応答に切り替えられません。** 定型文が返ると「読まれていない」と受け取られ、問題が一段重くなるためです。運用の設計とは、何を自動にするかより先に、何を自動にしないかを決めることです
- 受け皿のルール（7番）は自動応答にできません。何が来るか分からないものに定型文は書けないためです。**ここに落ちる件数が増えてきたら、そこがルールを足すべき場所です**
- 画面下に、届いている30件が「どのルールで・どの語に一致して・どう分類されたか」の一覧を出しています

---

## 【三】未返信の検知 — ここが中心です

初回返信の目標時間を過ぎた未対応を検知し、担当者へ再通知します。それでも動かない場合は店長へ引き上げます。

**上部の時計を進めると、通知が実際に発生します。** 30分／1時間／3時間／翌営業日の開店、の4つで進められます。

| 設定 | 初期値 | 画面から選べる値 |
|---|---|---|
| 初回返信の目標 | 1時間 | 30分／1時間／2時間 |
| 再通知の間隔 | 1時間ごと | 30分／1時間／2時間 |
| 再通知の上限 | 3回 | （設定オブジェクトで変更） |
| 店長へ引き上げ | 3時間超 | 2時間／3時間／6時間 |

- **未返信時間は営業時間の中だけで数えます。** 夜22時に届いた分を翌朝10時に「12時間放置」と数えると、毎朝すべてが超過になり、通知そのものが無視されるようになります
- 超過している件は、経過時間・超過分・発生した通知の回数・**店長への引き上げまであとどれだけか**（目盛つき）を一覧で表示します
- 「発生した通知」の履歴に、発生時刻・宛先（担当者／店長）・内容・対象のメッセージを1行ずつ残します。**次に発生する通知の予定**も表示します
- 再通知には上限（3回）を設けています。鳴り続ける通知は、やがて見られなくなるためです。上限に達した件は店長へ引き上げて担当者を変える、というのが実際の運用です
- **「対応済みにする」を押すまで通知は止まりません。通知を消すだけの操作は用意していません**

---

## 【四】営業時間外の扱い

LINEは営業時間を気にせず届きます。夜間・定休日に届いた分をどう扱うかを決めておかないと、翌朝には未読が積み上がり、古い順から埋もれます。

- 時間外に届いた分には、**受信と同時に自動返信**を送ります（営業時間と、次の営業日に返信する旨）
- 人の判断が要る分は、**翌営業日の開店時刻に対応キューへ入り、そこから未返信の計測が始まります**
- 答えが一つに決まる質問は、時間外でもその場で回答が返ります。翌日に持ち越しません
- 自動返信を「行う／行わない」で切り替えると、**お客さまが最初に反応を受け取るまでの時間**が比較できます（初期状態では 即時 対 平均17時間48分）

初期データでは、30件のうち9件が営業時間外の受信です（金曜夜・土曜夜・日曜1日・月曜の開店前）。うち人の判断が要る5件が翌営業日に持ち越されます。

## 【五】配信

一斉配信とセグメント配信を並べて比較します。友だちの数と月の配信回数を入力し、セグメントの条件を選ぶと、その場で計算し直します。

初期値（友だち1,200人・月4回）での比較です。**すべて想定値です。**

| 比較する項目 | 一斉配信 | セグメント配信 |
|---|---|---|
| 1回あたりの送信対象 | 1,200人 | 780人 |
| 月の送信通数 | 4,800通 | 3,120通 |
| 1回の配信あたりの想定ブロック率 | 0.9% | 0.2% |
| 月のブロック数（想定） | 43人 | 6人 |
| **6か月後の友だち数（想定）** | **941人** | **1,163人** |
| 読まれる人数（想定・1回あたり） | 492人 | 491人 |
| 来店につながる人数（想定・月） | 86人 | 162人 |

同じ配信回数でも、6か月後に残る友だちの数は **222人の差**になります。送る相手を4割減らしても読まれる人数はほとんど変わらない、という点も画面に出しています。**配信は、送った数ではなく読まれた数で見るものです。**

送信通数は料金プランの通数上限に直接効くため、想定プラン（5,000通）に対する余裕・超過も表示します。

## 【六】手作業との比較

月間の受信件数と、1件あたりの対応分数を入れると、削減時間が出ます。**自動応答で片づく割合は、いま設定している振り分けルールの結果（受信30件のうち12件＝40%）をそのまま使っています。** ルールを変えれば、この数字も変わります。

初期値（月640件・1件6分）での計算です。

| 内訳 | 件数 | 1件あたり | 月の合計 |
|---|---|---|---|
| いま：すべて人が対応 | 640件 | 6分 | 64.0時間 |
| 後：自動応答で完結 | 256件 | 0.5分 | 2.1時間 |
| 後：人が対応 | 384件 | 6分 | 38.4時間 |
| **削減時間** | — | — | **23.5時間／月（削減率37%）** |

**削減時間を大きく見せていません。**

- 人が対応する分の時間は短縮していません。文面を機械が書いても、判断は人が行うためです
- 自動応答で片づいた分にも、1件0.5分の確認時間を計上しています
- 未返信の検知による効果（放置されていた月235件が表面化する、時間外の受信に即時で反応が返る、担当者不在でも埋もれない）は、**時間には換算していません**。別表で「変わること」として記載しています

## 設定の差し替え

ファイル冒頭の設定オブジェクトを書き換えるだけで、別の業種の仕様になります。画面のコード本体には、店舗名も文面も時間も書いていません。

| 設定 | 内容 |
|---|---|
| `SHOP` | 店舗名・担当者名・店長名 |
| `BUSINESS_HOURS` | 営業時間・定休日・時間外の自動返信の文面 |
| `SLA_DEFAULT` / `SLA_PRESETS` | 初回返信の目標・再通知の間隔と上限・店長へ引き上げる時間 |
| `ROUTING_RULES` | 振り分けルール。判定に使う語、扱い（`auto` / `ack` / `human`）、自動応答の文面、`locked` の指定 |
| `MODES` / `STATUSES` | 扱いと分類の名前。`tone` で札の濃淡を指定 |
| `MESSAGES` | 受信メッセージ（30件）。`handled` で対応済みの初期状態を指定 |
| `BROADCAST` | 友だち数・配信回数・ブロック率・セグメントの定義 |
| `COMPARE` | 手作業との比較の初期値 |

飲食店なら「席の予約・アレルギーの確認」、整骨院なら「症状の相談・保険の適用」、教室なら「体験申込・振替」というように、ルールの名前と語句、自動応答の文面を差し替えれば同じ画面がそのまま動きます。**苦情を人に固定する（`locked: true`）という考え方は、業種を問わず共通です。**

---

## 数値の扱い

受信メッセージ・お客さまの名前・件数・削減時間・ブロック率は、**すべてデモ用の架空のデータおよび想定値**です。実在する店舗・人物・実績とは関係ありません。

**この画面はLINEのAPIには接続していません。** メッセージの送受信は行っておらず、ブラウザの中だけで動いています。入力・操作の内容はどこにも保存・送信されません（localStorage・Cookie・外部通信のいずれも使っていません）。ページを開き直すと最初の状態に戻ります。

---

## 実装時の構成

実際の導入では、**LINE公式アカウントの Messaging API** を使います。

- **受信** — Webhookをサーバー側で受け取り、自社のデータベースに保存します。この画面と同じ受信トレイは、この保存があって初めて成り立ちます
- **返信・配信** — サーバー側から送信します。APIのアクセストークンはブラウザに出しません
- **未返信の検知** — 定期実行（cronなど）で判定し、再通知はメール・チャットツール・スマートフォンの通知に流します。担当者がLINEの管理画面を見ていなくても届く経路にすることが要点です
- **配信の通数** — 送信できるメッセージの通数には料金プランごとに上限があり、上限を超えた分は追加費用が発生します。最新の通数と料金は、提供元の公式情報でご確認ください

**デモは React / Tailwind CSS（1ファイル構成・CDN読み込み・ビルド不要）／実装時は React・Next.js・Supabase・LINE Messaging API 構成**
