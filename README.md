# work-samples

業務システムと自動化ツールのサンプル集です。すべて実際に動作します。

現場の業務を実際に回してきた経験をもとに、**設定を差し替えるだけで別の業務にも使える**形で作っています。
それぞれのフォルダに、動かし方と設定の書き方を置いています。

---

## はじめに — 業務の悩み 索引

**▶ [ブラウザで開く](https://bty305-beep.github.io/work-samples/)** — どのサンプルを見ればよいか分からない場合は、こちらからどうぞ。

「見積り後に連絡が途切れて失注する」「電話が鳴りっぱなしで手が止まる」といった**症状から引ける索引**です。14件の悩みごとに、公開データによる裏づけ・何が起きているか・解決の型・該当するデモの場所をまとめています。

各サンプルの技術名ではなく、いま困っていることから探せます。数値の出典と注記はページ末尾にまとめてあります。

## 1. 受付一元化＋進捗自動連絡 — `demos/uketsuke-ichigenka/`

**▶ [ブラウザで開く](https://bty305-beep.github.io/work-samples/demos/uketsuke-ichigenka/)** — インストール不要、その場で操作できます。

電話・Webフォーム・LINE・来店の受付を1つの台帳にまとめ、**工程が進むたびに自動で連絡する**仕組みのデモです。上部のタブで4画面を切り替えられます。索引ページからの主な行き先で、意匠も索引ページと共通です。

| 画面 | 内容 | 直接開くURL |
|---|---|---|
| ① 業務棚卸し | 工程ごとの所要時間×月間件数を一覧にし、自動化できる／半自動化／人がやるべきの3分類に振り分け。時給スライダーで人件費換算 | `#tanaoroshi` |
| ② 受付 | お客さま側の入力フォーム。送信すると自動返信の文面が出ます | `#uketsuke` |
| ③ 管理画面 | 社内側の受付一覧と1件の詳細。「工程を進める」で自動連絡が履歴に1行増えます | `#kanri` |
| ④ 導入後の数字 | 4指標の導入前後と、削減時間・人件費換算 | `#suuji` |

- **緊急語の検出と、判定の根拠の表示** — 本文に緊急語が含まれると緊急と判定し、**判定に使った語をそのまま画面に出します**。判定に使う語の一覧も画面から確認できます。なぜ緊急になったのか説明できない状態を作らないためです
- **自動と担当を分けた対応履歴** — 履歴の各行に「自動」「担当」の別を付け、担当者が動かなくても送られた連絡がどれかを見て分かるようにしています
- **①の時給スライダーは④の人件費換算と連動**します
- **URLのハッシュで画面を直接指定できます** — 上表のとおり `#tanaoroshi` `#uketsuke` `#kanri` `#suuji`。索引ページからは、悩みごとに該当する画面へ直接リンクしています

業種を切り替えると、工務店・リフォーム／歯科医院／自動車整備に変わります。工程名・所要時間・月間件数・受付項目・ステージ名・緊急語が入れ替わりますが、**画面の構造とコードは完全に同じ**です。変えているのはファイル冒頭の `INDUSTRIES` の1オブジェクトだけで、業種を1つ足すと切替ボタンが1つ増えます。

所要時間・件数・導入後の数字は、すべて**デモ用の想定値**です。実在する企業の実績ではありません。受付フォームに入力した内容はどこにも保存・送信されません（localStorage・Cookie・外部通信のいずれも使っていません）。

**React / Tailwind CSS（1ファイル構成・CDN読み込み・ビルド不要）**

## 2. 業務管理システム — `html/gyomu-kanri.html`

**▶ [ブラウザで開く](https://bty305-beep.github.io/work-samples/html/gyomu-kanri.html)** — インストール不要、その場で操作できます。

複数拠点を持つ会社向けの管理システムです。人材管理・在庫管理・設備点検を、同じ仕組みで扱えます。意匠は索引ページと共通で、冒頭から索引ページに戻れます。

| 節 | 内容 |
|---|---|
| 一　誰として、どこを見ているか | 権限と所属拠点を切り替えると、見える範囲と使えるボタンがその場で変わります。権限ごとの一覧表つき |
| 二　一覧 | 検索・CSV書き出し・追加・編集・詳細・削除。入力欄は一覧の上に開きます |
| 三　項目定義 | いま表示している業務の項目定義を、そのまま表にして掲載 |
| 四　実案件ではどうなるか | 項目定義の置き場所、拠点ごとのデータ分離と権限、この画面と納品物の違い |

- **マルチテナント構成** — 拠点ごとにデータを分けつつ、本部では横断して表示
- **権限管理** — 本部管理者・拠点責任者・現場スタッフで、見える範囲と編集できる範囲が変わります。現場スタッフでは追加ボタンが消え、行の操作が「詳細」に変わります
- **状態は3段階で見分けます** — 通常／気に留める（要発注・要観察・休職）／手当てが要る（欠品・要修理）。臙脂を使うのは最後の1つだけです
- 一覧・検索・CSV出力（表示中の範囲をそのまま書き出し）、スマホ幅まで対応（表は横スクロール）

画面上部の「業務」を切り替えると、同じコードのまま人材管理・在庫管理・設備点検に変わります。変えているのはファイル冒頭の `SCHEMAS` の1オブジェクトだけで、表の列も入力欄も検索の対象もCSVの見出しも、すべてこの定義から組み立てています。車両管理や工具の貸出管理も、この定義を書き換えるだけで扱えます。

拠点・氏名・品名・件数・日付は、すべて**デモ用の想定値**です。実在する企業・人物・実績とは関係ありません。画面上で追加・編集・削除した内容はブラウザの中だけに保持され、どこにも保存・送信されません（localStorage・Cookie・外部通信のいずれも使っていません）。ページを開き直すと最初の状態に戻ります。

実案件では項目定義をデータベース側に持たせ、拠点ごとのデータ分離と権限制御をサーバー側で担保します（この画面は動作確認用に、権限の判定をブラウザ側で行っています）。

**React / Tailwind CSS（1ファイル構成・CDN読み込み・ビルド不要）／実案件は React・Supabase・Vercel 構成**

## 3. 予約・受付システム — `html/yoyaku-system.html`

**▶ [ブラウザで開く](https://bty305-beep.github.io/work-samples/html/yoyaku-system.html)** — インストール不要、その場で操作できます。

サロン・飲食店・教室で使える予約システムです。索引ページの悩み「ネット予約と電話予約が二重に入る」からの行き先で、意匠は索引ページと共通です。冒頭から索引ページに戻れます。

**画面は2つありますが、台帳は1つです。** 二重予約が起きるのは入口が多いからではなく、入口ごとに台帳が分かれているからです。このデモは、入口を減らさずに行き先だけをそろえると何が起きるかを示します。

| タブ | 節 | 内容 |
|---|---|---|
| お客さま画面 | 一〜四 | メニュー → 日付 → 時間 → お名前の4ステップ。選んだメニューの所要時間で空き枠を計算します |
| 店舗の管理画面（予約台帳） | 一　予約台帳 | 日付・CSV出力と、件数の内訳（うちネット／うち電話）・来店済みの売上 |
| 〃 | 二　空き状況 | 時間軸の帯で、担当（席・講師）ごとの埋まり具合 |
| 〃 | 三　予約一覧 | 受付経路と状態。状態を変えると帯と集計がその場で変わります |
| 〃 | 四　電話予約の入力 | 電話で受けた予約を、店舗がその場で同じ台帳に入れます |

- **入口が2つ、台帳は1つ。** 台帳の各行に受付経路（ネット／電話）が付き、集計にも内訳が出ます。どちらから入っても同じ台帳の同じ並びに入るので、突き合わせる作業がありません
- **画面上で両方向を確かめられます** — お客さま画面から予約を入れると、管理画面の「電話で受けた予約を台帳に入れる」からその枠が消えます。逆に電話予約を入れると、お客さま画面の時間選択から消えます
- **空き枠の判定は1か所だけ** — 両方の画面が `buildSlots` という同じ関数を見ています。判定を2か所に書くと、いつか片方だけ直して食い違うためです
- **重複予約を防止** — 所要時間を考慮するので、90分のメニューでは30分しか空いていない時間は選べません。担当（席）がすべて埋まった時間だけ取り消し線が付きます
- 定休日・営業時間を設定から反映。来店済み・キャンセル・無断キャンセルの記録、当日の売上集計、CSV出力（受付経路の列つき）

業種を切り替えると、サロン・飲食店・教室に変わります。変えているのはファイル冒頭の `BUSINESSES` だけで、店名・メニュー・担当（席・講師）・営業時間・定休日・入力項目が入れ替わります。画面の構造とコードは同じです。

店舗名・お客さまの氏名・電話番号・予約・売上は、すべて**デモ用の想定値**です。実在する店舗・人物・実績とは関係ありません。画面上で入れた予約はブラウザの中だけに保持され、どこにも保存・送信されません（localStorage・Cookie・外部通信のいずれも使っていません）。ページを開き直すと最初の状態に戻ります。

実案件では設定を管理画面から編集できるようにし、空き枠の判定をサーバー側に置いて、同時に押されたときも先着が勝つようにします。

**React / Tailwind CSS（1ファイル構成・CDN読み込み・ビルド不要）／実案件は React・Supabase・Vercel 構成**

## 6. データ収集ツール — `scrape-report/`

指定したページから必要な項目を集め、CSVと集計レポートを書き出します。

**別サイトを収集したい場合、コードは触りません。`config.json` を差し替えるだけです。**

- 取得項目・整形ルールをすべて設定ファイルに記述
- 「3,280円」→ `3280`、「2026年8月11日」→ `2026-08-11` のように表記を統一
- 重複行の除外、取得失敗ページの記録
- **CSVだけでなく集計レポートも同時に出力** — 内訳・分布に加えて、**取得できなかった項目の件数**まで出します

最後の項目が重要です。空欄が急に増えたときは、対象ページの構造が変わった合図になります。

**Python / requests / BeautifulSoup**

## 7. 定期的な情報収集の自動化 デモ — `demos/johoshushu/`

**▶ [ブラウザで開く](https://bty305-beep.github.io/work-samples/demos/johoshushu/)** — インストール不要、その場で操作できます。

上のデータ収集ツールが、**毎回どんなレポートを出すのか**を画面で確かめられるようにしたものです。競合の価格を毎朝チェックする、補助金の公募ページを定期的に開く、更新があったかを目視で確かめる。この一連の作業を機械に任せた場合に何が届くのかを示します。

| 節 | 内容 |
|---|---|
| 一　収集設定 | 対象サイト・取得項目・実行頻度を選ぶ。ここを変えると下の内容がその場で変わります |
| 二　収集結果 | 取得したデータの一覧。今回と前回を横に並べて表示 |
| 三　差分レポート | **中心の画面。** 変わった行だけを、値上がり・値下がり・新規・消えた・項目の変更に分けて表示 |
| 四　通知ルール | 「価格が5％以上下がったら」などの条件。該当行が差分レポートで強調されます |
| 五　実行履歴 | いつ実行され、何件取得し、何件変わったかの記録 |
| 六　手作業との比較 | 対象件数と目視秒数を入れると削減時間が出ます |

- **変化なしの行は、確認しなくてよい行です。** 延べ30件のうち17件が「変化なし」で、見るべきは残り13件、うち通知条件に当てはまるのは9件、と画面に出ます。全件を見比べる作業がここでなくなることが伝わる形にしています
- **設定を変えると結果が変わります** — 取得項目から「販売価格」を外すと値上がり・値下がりの区分が消え、価格を参照する通知ルールが自動的に無効になります。通知のしきい値を5％→2％に下げると該当件数が増えます
- **しきい値の境目が分かるデータを入れてあります** — +3.1％ と −2.5％ の行があり、5％では通知されません。「変化したが、知らせるほどではない」を切り分けていることが画面上で確認できます
- **実行履歴には取得に失敗した回も残ります。** 何も届かない状態を「変化がなかった」と取り違えないためです
- **用途を切り替えられます** — 「競合の価格・在庫」と「補助金・公募情報」。同じ画面のコードのまま、対象・項目・通知条件・データだけが入れ替わります。ファイル冒頭の `CONFIG` と `PRESETS` を差し替えるだけです

**掲載しているデータはすべてデモ用の架空のものです。実在するサイトへのアクセスは一切行っていません。** 「前回取得分」と「今回取得分」の2世代のデータをファイル内にあらかじめ持たせ、実行ボタンで両者を突き合わせています。

実際の納品物は、サーバー上で定期実行し差分レポートをメールで送るPythonスクリプトです（この画面は届くレポートの中身を先に確認するためのもの）。収集先サイトの利用規約と robots.txt は着手前に確認し、許容される範囲でのみ実施します。

**React / Tailwind CSS（デモ）**

## 8. Excel業務の自動化キット — `excel-kit/`

毎月くり返している作業を、設定ファイルを書くだけで自動化します。Excelはそのまま使い続けられます。

| ジョブ | 内容 |
|---|---|
| `reconcile` | 2つの表を突き合わせて、**合わない箇所だけ**を洗い出す |
| `aggregate` | 複数のファイルを1つにまとめて、条件別に集計する |
| `fill` | 決まった書式に流し込んで帳票や文面を作る |

**突合が中心です。** 請求と入金、発注と納品、勤怠と給与。手作業だと見落としが出て、しかも見落としたこと自体に気づけない作業です。

同梱サンプルで実際に検出される内容です。

- **440円の差** … 振込手数料が引かれている
- **50,000円の差** … 一部入金
- **請求のみ2件** … 未入金
- **入金のみ2件** … 請求番号ではなく取引先名で振り込まれている

`inv-2026-0801` と `INV-2026-0801` を同一と見なすなど、キーの表記ゆれも設定で吸収します。突合が失敗する原因のほとんどがここです。

**Python / pandas / openpyxl**

## 9. Excel突合の自動化 デモ — `demos/excel-shogo/`

**▶ [ブラウザで開く](https://bty305-beep.github.io/work-samples/demos/excel-shogo/)** — インストール不要、その場で操作できます。

上の自動化キットの `reconcile` が何をしているのかを、**画面で確かめられる**ようにしたものです。銀行の入金明細（30行）と売掛帳（30行）を突き合わせ、**一致・不一致・要確認**の3分類で出します。

- **なぜその分類になったかを1行ずつ表示** — 「差額660円」「日付が1日ずれています」「表記ゆれを正規化して名寄せしました。効いたルール：…」
- **正規化ルールをその場で切り替えられます** — 全角半角、株式会社／（株）／カブシキガイシャ、空白、記号と付記、日付の書式。外すと結果がその場で変わります
- **正規化なし 要確認22件 → 推奨設定 要確認7件。** 集計タイルに両方の件数を併記しているので、ルールが何件分の目視を消しているかが分かります
- 金額の許容差（円）・日付の許容ずれ（日）も画面から変更できます
- 件数と1件あたりの目視秒数を入れると、削減時間が出ます（突合結果の比率をそのまま使用）

サンプルデータには、1円違い・1日ずれ・全角混在・半角カナ・摘要への付記・同名重複・似ているだけの別会社など、**実務でよくある崩れ方**を入れてあります。**迷ったら要確認に落とす**方針です。誤って消し込まれるほうが、目視の手間より高くつくためです。

実際の納品物は、同じ処理をお手元のExcelに対して行うPythonスクリプトです（この画面は動作確認用）。

**React / Tailwind CSS（デモ）**

## 10. EC向け問い合わせ自動応答 デモ — `demos/ec-faq-bot/`

**▶ [ブラウザで開く](https://bty305-beep.github.io/work-samples/demos/ec-faq-bot/)** — インストール不要、その場で操作できます。

索引ページの悩み「問い合わせに毎回同じ返信を書いている」からの行き先です。意匠は索引ページと共通で、冒頭から索引ページに戻れます。

**狙いは問い合わせを減らすことではなく、定型の質問を自動応答に回して、判断が要るものだけを人の手元に残すことです。** 同じ返信を毎回書いてしまうのは、質問の大半が定型だからです。定型の質問に定型の答えを返す作業は、人がやっても機械がやっても中身が変わりません。

| タブ | 節 | 内容 |
|---|---|---|
| お客さま側の画面 | 一　やり取り | 選択式 → AI → 有人の3段階を実際に辿れます。右に「この段階までで片づく割合」を常時表示し、いまいる段階に印を付けます |
| 運営側の一元管理 | 一　内訳 | 段階ごとに何件片づき、何件が次に残るかを積み上げの帯と表で表示 |
| 〃 | 二　受信トレイ | LINE・Gmail・問い合わせフォームを1つの受信トレイに集約。状態と流入元で絞り込み |

| 段階 | ここで片づく | 次に残る |
|---|---|---|
| 受け付けた全件 | — | 1,000件 |
| 選択式の自動応答 | 430件（43%） | 570件 |
| AIの自動応答 | 190件（19%） | 380件 |
| 有人対応 | — | **380件（38%）** |

- **なぜ人に回ってきたのかを、開かずに読めます** — 「人の判断が必要」の行には、自動返信を止めている理由（返金の決裁が必要／法人取引は営業判断／配送事故の調査が必要など）を一覧の時点で1件ずつ表示します
- **判断は人、文面作成はAI** — 人に残った行も、ボタン1つでAIに返信の下書きを作らせ、確認・編集してから送信できます
- **削減率を大きく見せていません** — AI下書きを使った250件は人が確認して送るため有人対応に数えます。削減率は「人の手を一切介さずに完結した件数」だけで計算しています
- **画面をまたいで繋がります** — お客さま側で担当者に引き渡すと、運営側の受信トレイに「人の判断が必要」として1件増え、上部の集計もその場で変わります

問い合わせ件数・削減率・お客さまの氏名・注文情報は、すべて**デモ用の想定値**です。実在する企業・人物・実績とは関係ありません。AIの応答も、デモのためあらかじめ用意した文面をキーワード一致で返しています。localStorage・Cookie・外部通信のいずれも使っていません。

選択肢のツリー・AIの応答・ステータス定義は、ファイル冒頭の設定オブジェクト（`FAQ_TREE` / `AI_RESPONSES` / `STATUSES`）にまとめています。ブランドごとの差し替えはこの部分だけで完結します。実装時は、AIの回答生成も返信下書きの作成も、各チャネルの受信・送信もすべてサーバー側で行い、APIキーはブラウザに出しません。

**React / Tailwind CSS（1ファイル構成・CDN読み込み・ビルド不要）／実装時は React・Next.js・Supabase・LINE Messaging API・Gmail API 構成**

## 14. LINE公式アカウント 運用設計 デモ — `demos/line-unyo/`

**▶ [ブラウザで開く](https://bty305-beep.github.io/work-samples/demos/line-unyo/)** — インストール不要、その場で操作できます。

索引ページの悩み「LINE公式を作ったが、放置されている」からの行き先です。意匠は索引ページと共通で、冒頭から索引ページに戻れます。

**放置は、担当者の性格の問題ではなく設計の問題です。** 返ってこないのは答えにくい件です。予約が取れない、値引きを求められた、苦情が来た。人は答えにくい件を後回しにします。問題は、後回しにしたことを誰も検知していないことです。**このデモの中心は自動応答ではなく、未返信の検知のほうです。**

| タブ | 内容 |
|---|---|
| 一　受信トレイ | 届いたメッセージ30件を、未対応・自動応答済・要対応の3分類で表示。開くと本文・当たったルール・一致した語・自動返信の文面・経過時間が読めます |
| 二　振り分けルール | 何を自動応答に回し、何を人に残すかを設定。**切り替えると上の要約と受信トレイの分類がその場で変わります** |
| 三　未返信の検知 | 目標時間を過ぎた未対応を検知し、担当者へ再通知、さらに超えると店長へ引き上げ。時計を進めると通知が実際に発生します |
| 四　営業時間外の扱い | 時間外の自動返信と、翌営業日の対応キューへの入り方。自動返信の有無で待ち時間を比較 |
| 五　配信 | 一斉配信とセグメント配信の比較。想定ブロック率と6か月後の友だち数の差 |
| 六　手作業との比較 | 月間件数と1件あたりの分数を入れると削減時間が出ます |

初期状態（デモ内の現在時刻 8/17(月) 11:30）では、受信30件のうち自動応答済12件・未対応5件・**要対応11件**。最も長い未返信は**10.8営業時間**で、5回の通知を経て店長へ引き上げ済みです。

- **未返信時間は営業時間の中だけで数えます** — 夜22時の受信を翌朝に「12時間放置」と数えると、毎朝すべてが超過になり、通知そのものが無視されるようになります
- **通知の履歴を1行ずつ残します** — 発生時刻・宛先（担当者／店長）・内容・対象のメッセージ。次に発生する通知の予定も表示します
- **「対応済みにする」を押すまで通知は止まりません** — 通知を消すだけの操作は用意していません。再通知には上限（3回）があり、超えると店長へ引き上げます
- **苦情は自動応答に切り替えられません** — 定型文が返ると「読まれていない」と受け取られ、問題が一段重くなるためです。運用の設計とは、何を自動にするかより先に、何を自動にしないかを決めることです
- **受付の自動返信を送っても、人の対応は残ります** — 扱いを「自動応答で完結／受付だけ自動返信／人が対応」の3つに分け、自動化しても消えない分が見えるようにしています
- **削減時間を大きく見せていません** — 人が対応する分は短縮せず、自動応答で片づいた分にも1件0.5分の確認時間を計上しています。未返信の検知による効果は時間に換算していません

受信メッセージ・氏名・件数・削減時間・ブロック率は、**すべてデモ用の架空のデータおよび想定値**です。**LINEのAPIには接続していません。** localStorage・Cookie・外部通信のいずれも使っていません。

振り分けルール・営業時間・目標時間・配信の想定値は、ファイル冒頭の設定オブジェクト（`ROUTING_RULES` / `BUSINESS_HOURS` / `SLA_DEFAULT` / `BROADCAST` / `MESSAGES`）にまとめています。飲食店・整骨院・教室など、他業種への転用はこの部分の差し替えだけで済みます。実装時は Messaging API のWebhookをサーバー側で受け、未返信の検知は定期実行で判定して、メールやチャットツールへ通知を流します。配信できる通数には料金プランごとの上限があります。

**React / Tailwind CSS（1ファイル構成・CDN読み込み・ビルド不要）／実装時は React・Next.js・Supabase・LINE Messaging API 構成**

## 15. 見積書・請求書の作成 デモ — `demos/mitsumori-seikyu/`

**▶ [ブラウザで開く](https://bty305-beep.github.io/work-samples/demos/mitsumori-seikyu/)** — インストール不要、その場で操作できます。

索引ページの悩み「見積書・請求書を毎回手で作っている」からの行き先です。意匠は索引ページと共通で、冒頭から索引ページに戻れます。

「前回のファイルをコピーして書き換えている」「単価の間違いが起きる」「発行漏れがある」。**この3つは、単価と帳票の状態を持つ場所がなく、都度ファイルを複製していることから同時に起きています。** マスタから帳票を作る形にすると、3つとも消えます。

| 画面 | 内容 |
|---|---|
| 一　商品マスタ | 商品12件を品番・品名・単位・単価・税区分で保持。**単価と税区分は画面上で直せます**（直した値は、これから作る帳票に反映されます） |
| 二　発行状況の一覧 | **ここが中心です。** 未発行・発行済・入金済・期日超過・見積のままの5区分。発行漏れと回収漏れが目で分かります |
| 三　見積書の作成 | マスタから選んで数量を入れるだけ。**単価は入力しません。** 帳票番号は自動採番 |
| 四　見積書から請求書へ | 1回押すだけで請求書に。**金額を入力しなおす場面はありません。** 支払期日は取引先の支払条件から自動 |
| 五　インボイス対応 | 適格請求書の記載事項6項目の対応表。端数処理（切り捨て・四捨五入・切り上げ）を画面上で切り替えられます |
| 六　手作業との比較 | 月間の発行件数と1件あたりの分数を入れると、削減時間が出ます |

- **期日超過は人が印を付けません** — 支払期日と基準日を比べて自動で付き、何日超過しているかも出ます。臙脂で強調しているのはこの行だけです
- **「見積のまま」を独立した区分にしています** — 見積書は出したのに請求に進んでいないものです。受注したのに請求し忘れている場合が、ここに現れます
- **端数処理は税率ごとに1回だけ** — 行ごとに処理をすると、適格請求書として認められる方法から外れます。切り替えると帳票と一覧の金額がその場で変わります

サンプルは取引先5社・商品12件・帳票15件で、**期日超過3件・見積のまま3件・軽減8%と標準10%が混在する伝票・値引きが入った伝票**を含みます。すべて架空です。localStorage・Cookie・外部通信のいずれも使っていません。

**税制の取扱い（端数処理の方法、軽減税率の対象、値引きや返品の扱いなど）は、顧問税理士に確認していただくことを前提としています。** 実際の納品物は、お手元のExcelや会計ソフトの様式に合わせた形になります。

**React / Tailwind CSS（1ファイル構成・CDN読み込み・ビルド不要）**
