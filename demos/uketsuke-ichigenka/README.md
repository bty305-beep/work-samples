# 受付一元化＋進捗自動連絡 デモ

電話・Webフォーム・LINE・来店の受付を1つの台帳にまとめ、工程が進むたびに自動で連絡する仕組みのデモです。
`index.html` をブラウザで開くだけで動きます（インストール不要）。

> **掲載している所要時間・件数・導入後の数字は、すべてデモ用の想定値です。**
> 実在の企業の実績を示すものではありません。
> 受付フォームに入力した内容は、どこにも保存・送信されません。ブラウザのメモリ上にだけ置き、
> ページを再読み込みすると消えます（localStorage・Cookie・外部通信のいずれも使っていません）。

---

## なぜこの順番なのか

中小企業のAI導入率は **20.4%** にとどまり、最大の障壁は
「具体的な活用場面が不明」**35.6%**、「導入を推進する人材がいない」**32.0%** でした
（中小機構・商工中金 2026年調査）。ツールの性能ではなく、**どこに使うか決められないこと**が止めています。

AI導入の失敗事例は「業務棚卸しをせずにツールだけ入れた」ケースに集中しています。
成功している企業は、導入前に30〜50業務を棚卸ししています。

そこでこのデモは、順番を固定しました。

```
① 業務棚卸し → ② 受付の一元化 → ③ 進捗の自動連絡 → ④ 測り直し
```

①を飛ばして②③から入ると、「入れたが使われていない」状態になります。

**どこを削るか**も、棚卸しの段階で決めています。求人票の検索件数は
電話対応 618万件／問い合わせ対応 359万件／データ入力 202万件。ここに人が張り付いています。
一方で、Googleの口コミ120社を分析すると、低評価の最大の要因は
**「連絡が来ない」「ネット予約と窓口予約が重複した」** でした。
顧客が催促するまで情報が出てこない状態が、そのまま失注につながっています。

②と③は、この2つだけを狙って作っています。

## 画面の構成

上部のタブで4画面を切り替えられます。

| タブ | 内容 |
|---|---|
| ① 業務棚卸し | 工程ごとに「1件あたりの所要分 × 月間件数 = 月の合計時間」を表示。3分類でタグ付けし、削減時間と人件費換算を上部にサマリ |
| ② 受付 | お客さま側の問い合わせフォーム。送信すると自動返信の文面が出る。緊急語を含む場合は「緊急」と判定し、根拠の語を表示 |
| ③ 管理画面 | 左が受付一覧、右が1件の詳細。工程をステップ表示し、「工程を進める」で前進。履歴に「自動／担当」のラベル |
| ④ 導入後の数字 | 一次返信までの時間・催促件数・予約の重複・転記時間を導入前後で比較。削減時間の合計と人件費換算 |

---

### ① 業務棚卸し

工程を **自動化できる／半自動化／人がやるべき** の3つに分類します。
削減率は分類ごとの仮置き（80% / 40% / 0%）で、実際の案件では工程ごとの実測値に置き換えます。

上部のサマリに、対象業務の合計時間・削減できる時間・人件費換算を出します。
時給はスライダーで変更でき、④の人件費換算にもそのまま反映されます。

各行にCSSの横バーを付け、時間の大きい工程が一目で分かるようにしています。

**中核業務（施工・診療・診断）は、はじめから自動化の対象外にしています。**
表を「受付・事務まわり（自動化の検討対象）」と「中核業務（自動化の対象外・別掲）」の2区分に分け、
削減見込みの計算には中核業務を一切含めていません。バーの相対比較も区分ごとに独立させています。

事務作業を減らすのは、この中核業務に時間を戻すためです。逆にすると、短期の時間削減と引き換えに品質が落ちます。

### ② 受付（顧客側）

電話・Webフォーム・LINE・来店の4つの入口が、すべて同じ台帳の1行になることを画面上で説明します。
入口ごとに保管場所が分かれていることが、そのまま予約の重複を生んでいるためです。

緊急判定は**語句一致**です。判定と同時に、**根拠になった語をそのまま画面に出します**。
「判定に使う語の一覧を見る」から、その業種で使っている全語も確認できます。

精度より先に、**なぜ緊急になったのかを説明できること**を優先しました。
本番ではここに文脈の判定を足しますが、判定に使った語の表示は残す想定です。

送信した内容は、③の受付一覧の先頭に追加されます（ブラウザのメモリ上のみ）。

### ③ 管理画面（社内側）

「工程を進める」を押すと、その時点で自動連絡が送られ、対応履歴に1行追加されます。

履歴の各行には **「自動」「担当」** のラベルを付けています。理由は2つです。

1. 顧客に何が届いているかを、担当者が履歴だけで把握できる
2. 「連絡していないのに連絡したことになっている」状態を作らない

「担当者メモを追加」から、人が対応した記録も足せます（「担当」として記録されます）。

### ④ 導入後の数字

一次返信までの時間・催促件数・予約の重複件数・台帳への転記時間を、導入前後で並べます。
①の分類と削減率から計算した削減時間の合計と人件費換算も出します。

数値はすべてデモ用の想定値です。実際の案件では、**着手前に同じ4項目を1か月測ってから**始めます。
測っていない項目は、あとから効果を説明できないためです。

## 業種の切り替え

画面上部で **工務店・リフォーム／歯科医院／自動車整備** を切り替えられます。

切り替えると、工程名・所要時間・月間件数・受付項目・ステージ名・緊急語・導入後の数字が変わります。
**画面の構造とコードは完全に同じです。** 変えているのは、ファイル冒頭の `INDUSTRIES` の1オブジェクトだけです。

| | 工務店・リフォーム | 歯科医院 | 自動車整備 |
|---|---|---|---|
| 工程 | 受付→現地調査→見積提示→契約→着工→完了 | 受付→初診カウンセリング→検査・診断→治療計画の説明→治療→メンテナンス移行 | 受付→入庫→診断・見積→作業承認→整備作業→納車 |
| 中核業務 | 施工・現地調査・仕様決定 | 診療・検査/診断・治療計画の説明 | 整備作業・診断・完成検査 |
| 緊急語の例 | 雨漏り／至急／止まらない | 痛い／腫れ／眠れない | 警告灯／異音／ブレーキ |

受付台帳は業種ごとに独立して保持されるため、切り替えても、それぞれの工程の進み具合は保たれます。

## 設定の書き方

ファイル冒頭の2つのオブジェクトだけを触ります。画面側のコードは、業種の中身を一切知りません。

### `CONFIG` — 配色と共通設定

```js
const CONFIG = {
  theme: { primary: "#6b2350", accent: "#bf5730", /* ... */ },
  kinds: {
    auto:  { label: "自動化できる", cut: 0.8, hint: "..." },
    semi:  { label: "半自動化",     cut: 0.4, hint: "..." },
    human: { label: "人がやるべき", cut: 0.0, hint: "..." },
  },
  defaultWage: 2200,
};
```

`theme` はCSSカスタムプロパティとして注入されるため、ここを書き換えるだけで全体の配色が変わります。
`kinds.cut` が削減率です。

### `INDUSTRIES` — 業種定義

1業種＝1オブジェクトです。ここに1つ足すと、画面上の切替ボタンが1つ増えます。

```js
const INDUSTRIES = {
  koumuten: {
    label: "工務店・リフォーム",
    orgName: "株式会社◯◯工務店",
    customerWord: "お客さま",     // 画面内の呼称（患者さま 等）
    coreWord: "施工",              // 中核業務の呼び方
    stages: ["受付", "現地調査", "見積提示", "契約", "着工", "完了"],
    channels: [ { key: "tel", label: "電話", note: "..." }, /* 4件 */ ],
    tasks: [
      // group: "office"（自動化の検討対象） / "core"（中核業務・対象外）
      { group: "office", name: "受付内容の台帳への転記", min: 6, cnt: 185, kind: "auto", note: "..." },
      { group: "core",   name: "施工（現場作業）",       min: 1200, cnt: 22, kind: "human", note: "..." },
    ],
    form: {
      lead: "...",
      fields: [
        { key: "body", label: "ご相談内容", type: "textarea", required: true, scan: true },
      ],
      samples: { normal: { /* ... */ }, urgent: { /* ... */ } },
    },
    urgentWords: ["雨漏り", "至急", /* ... */],
    reply: { normalLead: "...", urgentLead: "...", closing: "..." },
    seeds: [ /* 管理画面の初期データ */ ],
    metrics: [ { label: "...", before: "...", after: "...", note: "..." } ],
  },
};
```

主なキーは次のとおりです。

| キー | 役割 |
|---|---|
| `stages` | 工程。③のステップ表示と「工程を進める」の順序になります |
| `tasks[].group` | `office` = 自動化の検討対象／`core` = 中核業務。`core` は削減計算から除外されます |
| `tasks[].kind` | `auto` / `semi` / `human`。`CONFIG.kinds` の削減率が適用されます |
| `form.fields[].scan` | `true` の項目だけが緊急語の判定対象になります |
| `urgentWords` | 緊急と判定する語。画面から一覧を確認できます |
| `metrics` | ④の導入前後の比較。文字列なので単位は自由です |

## 技術構成

- React 18 + Tailwind CSS（いずれもCDN）、Babel standalone による1ファイル完結
- ビルド不要。`index.html` をそのまま開けば動きます
- **localStorage 不使用**（Cookie・外部送信もなし）。状態はReactのstateのみで、リロードすると初期状態に戻ります
- スマートフォン幅（390px）まで対応。横スクロールは発生しません

本番実装では、`INDUSTRIES` を管理画面から編集できる設定データに外出しし、
台帳をDBに、自動連絡をメール／SMS／LINEの送信基盤に接続します。
画面の構造とデータの形は、このデモから変えません。
