# EC向け問い合わせ自動応答 デモ

`index.html` をブラウザで開くだけで動きます。インストール・ビルド不要、1ファイル完結です。意匠は索引ページ（リポジトリ直下の `index.html`）と共通で、冒頭から索引ページに戻れます。

お客様の問い合わせが

**選択式の自動応答 → AIの自動応答 → LINE / Gmail / 問い合わせフォーム → 一元管理 → AI返信・AI下書き → 必要な案件のみ有人対応**

と流れていく過程を、実際に操作しながら確認できます。

---

## この画面が言いたいこと：定型は自動、判断は人に

同じ返信を毎回書いてしまうのは、質問の大半が定型だからです。定型の質問に定型の答えを返す作業は、人がやっても機械がやっても中身が変わりません。

**狙いは問い合わせを減らすことではなく、定型の質問を自動応答に回して、判断が要るものだけを人の手元に残すことです。**

| 段階 | ここで片づく | 次に残る | この段階が受けるもの |
|---|---|---|---|
| 受け付けた全件 | — | 1,000件 | 直近30日に届いたすべての問い合わせ |
| 選択式の自動応答 | 430件（43%） | 570件 | 定型的な質問。選択肢を辿るだけで回答に到達します |
| AIの自動応答 | 190件（19%） | 380件 | 言い回しが違っても意図を判定。選択肢に無い質問にも回答します |
| 有人対応 | — | **380件（38%）** | 返金・クレーム・例外対応のみ。AI下書きつきで受け取ります |

**削減率 62.0%** — 目標帯 50〜70% の中央です。画面上部に、この内訳を積み上げの帯と段階ごとの表で出しています。削減がどの段階から来ているかが、数字を追わなくても見て分かります。

有人対応380件のうち250件には**AIの返信下書きが付いています**。ただし人が確認して送信するため、これは削減率には含めていません。削減率は「人の手を一切介さずに完結した件数」だけで計算しています。数字を大きく見せないためです。

## 【1】お客さま側の画面

1. **選択式の自動応答** — ECでよくある6分類（配送状況／返品交換／サイズ・素材／支払い／キャンセル・変更／在庫）から選択肢を辿ると回答に到達します。階層は何段でも設定できます（返品交換は3階層）
2. **AIの自動応答** — 「解決しなかった」を押すと自由入力に切り替わります。言い回しが違っても意図を判定して回答します
3. **有人対応** — AIでも解決しない場合、担当者へのフォームが出ます。連絡方法（LINE / Gmail / 問い合わせフォーム）を選んで送信できます

画面の右に、**その段階までで何割が片づくか**の想定値を常時表示し、いまいる段階に罫線で印を付けています。今どこにいて、あと何割がこの先に流れるのかが分かります。

送信した分は、**運営側の一元管理画面にそのまま「人の判断が必要」として追加されます。** 上部のタブで切り替えて確認できます。

---

## 【2】運営側の一元管理

- LINE / Gmail / 問い合わせフォームからの問い合わせを、**1つの受信トレイ**に集約
- 流入元は色ではなく**名前**で区別します（意匠がアクセント紺1色のため）
- ステータスは4種類 — 自動で解決済み / 下書きあり・要確認 / 人の判断が必要 / 対応済み
- **「人の判断が必要」の行は、開かなくても一覧の時点で「自動返信を止めている理由」が読めます。** なぜ人に回ってきたのか説明できない状態を作らないためです
- 「下書きあり・要確認」の行を開くと返信文が表示され、そのまま送信するか、編集してから送信できます
- 「人の判断が必要」の行は、ボタン1つでAI下書きを作らせることもできます（判断は人、文面作成はAI）
- ステータス・流入元での絞り込み

## 設定の差し替え

ファイル冒頭の設定オブジェクトを書き換えるだけで、別ブランドの仕様になります。コード本体は触りません。

| 設定 | 内容 |
|---|---|
| `BRAND` | ブランド名・挨拶文・受付時間 |
| `BASELINE` | 実績のベースライン。削減率はここから算出されます |
| `TARGET` | 目標帯（初期値 50〜70%） |
| `STAGE_DEFS` | 3段階の名前と説明。想定解決率は `BASELINE` から自動算出 |
| `FAQ_TREE` | 選択式の応答ツリー。`children` で入れ子、`answer` で回答 |
| `AI_RESPONSES` | AIの応答。キーワードと返答文の組 |
| `ESCALATION_FORM` | 有人対応フォームの入力項目 |
| `SOURCES` | 流入元の定義（ラベル） |
| `STATUSES` | ステータス定義。`counts` で削減率の集計区分、`tone` で札の濃淡を指定 |
| `INBOX_SEED` | 受信トレイの初期データ |

## 数値の扱い

問い合わせ件数・削減率・お客さまの氏名・注文情報は、**すべてデモ用の想定値**です。実在する企業・人物・実績とは関係ありません。画面上の操作内容はブラウザの中だけに保持され、どこにも保存・送信されません（localStorage・Cookie・外部通信のいずれも使っていません）。ページを開き直すと最初の状態に戻ります。

---

## 実装時の構成

本デモは画面確認用のため、AIの応答はあらかじめ用意した内容をキーワード一致で返しています（APIは呼びません）。

実装時は次の処理を**すべてサーバー側**で行います。

- **AIによる回答生成・返信下書きの作成** — 社内のFAQ・過去の対応履歴を参照して生成。APIキーはブラウザに出しません
- **LINE（Messaging API）／Gmail（Gmail API）／フォームPOSTの受信** — 各チャネルのWebhookを受け取り、共通のスキーマに正規化して1つのテーブルに保存します。一元管理画面が成り立つのはこの正規化があるためです
- **返信の送信** — 受信と同じ経路を逆にたどるため、担当者はチャネルを意識せずに返信できます

**デモは React / Tailwind CSS（1ファイル構成・CDN読み込み・ビルド不要）／実装時は React・Next.js・Supabase・LINE Messaging API・Gmail API 構成**
